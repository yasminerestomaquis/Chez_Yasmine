# Caisse / POS — Chez Yasmine

## Routes NestJS

```
POST /establishments/:establishmentId/sales                     { items, payments, discount?, customerId?, tableId?, orderId?, orderNumber?, marketNumber? }
GET  /establishments/:establishmentId/sales?day=YYYY-MM-DD
GET  /establishments/:establishmentId/sales/last-order-number   { orderNumber: number | null }  — suggestion, jamais imposée
GET  /establishments/:establishmentId/sales/last-market-number  { marketNumber: number | null }  — suggestion, jamais imposée
GET  /establishments/:establishmentId/sales/:saleId
POST  /establishments/:establishmentId/sales/:saleId/refund
PATCH /establishments/:establishmentId/sales/:saleId/items/:itemId       { quantity }
PATCH /establishments/:establishmentId/sales/:saleId/payments/:paymentId { method }
```

`pos.sell` pour créer/consulter, `pos.refund` pour annuler une vente entière, `pos.correct` pour corriger une ligne déjà enregistrée (quantité, mode de paiement) sans l'annuler — trois permissions distinctes (permissions du catalogue de la Phase 3 — un caissier peut vendre sans forcément pouvoir rembourser/corriger, selon le rôle ; `pos.correct` séparée de `pos.refund` depuis le 2026-09-16, voir plus bas).

## Logique métier

Reprise et adaptée du prototype v1 déjà validé :

- `pos-math.ts` : `computeCartTotals` (sous-total, remise en montant ou pourcentage, jamais négative) et `validatePayments` (la somme des paiements doit correspondre exactement au total à ±0,01 près, un paiement crédit exige un client).
- `credit-math.ts` : `applyCreditSale` (plafonne au `creditLimit` du client), partagé avec la Phase 11 (remboursements de crédit).

## `SalesService.create`

1. Recharge les produits **depuis la base**, jamais depuis les prix envoyés par le client — le prix de vente appliqué est toujours `product.salePrice` au moment de la vente, **sauf** pour un produit d'une catégorie à prix variable (`Category.hasVariablePricing`, ex. Poulets/Poissons/Plats africains — voir `docs/api/catalog.md`) : `product.salePrice` y est `null` en catalogue, donc le caissier saisit un prix dans l'UI (`PosPage._promptManualPrice`), transmis en `SaleItemDto.unitPrice` ; le serveur l'exige dans ce cas (`BadRequestException` sinon) et l'ignore pour tout autre produit — le client ne devient jamais source de vérité sur le prix d'un produit à prix fixe, défense en profondeur cohérente avec le reste de l'application (CLAUDE.md, « le client n'est jamais une source de confiance »).
2. Vérifie le stock disponible **par produit, quantités agrégées entre toutes les lignes du panier qui le concernent** (voir « Deux corrections » ci-dessous) *avant* d'ouvrir une transaction (échoue vite, sans effet de bord).
3. Calcule les totaux et valide le paiement (fonctions pures ci-dessus).
4. Si un paiement `credit` est présent, vérifie le plafond de crédit du client *avant* la transaction.
5. Transaction Prisma unique : décrémente le stock de chaque produit (une seule requête conditionnelle par produit, voir ci-dessous) + écrit un `StockMovement` de type **`sale`** par ligne (jamais accepté sur la route de saisie manuelle du stock, Phase 6) + crée la `Sale`/`SaleItem`/`Payment` + si crédit, crée le `Credit` et met à jour `customer.creditBalance`.

Le nom du produit est recopié dans `SaleItem.name` au moment de la vente (indépendant d'un renommage ultérieur du produit — un reçu ne doit jamais changer rétroactivement).

### Deux corrections sur la vérification du stock (décision actée 2026-09-13)

Un même produit peut légitimement apparaître sur **plusieurs lignes** d'une même vente : les catégories à prix variable (Poulets, Poissons, Plats africains) n'ont pas de prix catalogue, donc chaque ajout au panier avec un prix différent crée une nouvelle ligne (`PosPage._addToCart`/`OrdersService.addItem`, voir ci-dessous « N° de commande / N° de marché »). Deux bugs en découlaient :

1. **Vérification par ligne plutôt que par produit** — comparer chaque ligne isolément au stock du produit laissait passer une vente dont la **somme** des quantités du même produit dépassait le stock réel (ex. stock = 3, deux lignes de 2 à des prix différents : 2 < 3 pour chacune prise séparément, mais 4 > 3 au total). Corrigé : les quantités sont désormais agrégées par `productId` (`quantityByProductId`) avant toute vérification, aussi bien pour le contrôle rapide en amont que pour la décrémentation elle-même.
2. **Vérification hors transaction (course entre ventes concurrentes)** — le contrôle initial (`product.findMany`, avant la transaction) restait un simple "lu-puis-écrit" : deux ventes du même produit lancées presque simultanément pouvaient chacune passer ce contrôle avant qu'aucune des deux n'ait encore décrémenté, et vendre ensemble plus que le stock disponible — sans qu'aucune contrainte de base n'empêche `stock_quantity` de devenir négatif. Corrigé : la décrémentation, dans la transaction, utilise désormais `product.updateMany({ where: { id, stockQuantity: { gte: quantity } }, data: { stockQuantity: { decrement: quantity } } })` — une requête SQL atomique par produit. Le verrou de ligne pris par Postgres pendant cet `UPDATE` sérialise deux décrémentations concurrentes du même produit ; si le stock ne suffit plus au moment où la requête s'exécute réellement (`count === 0`), toute la transaction est annulée (`ConflictException`), y compris la `Sale` déjà construite dans le même bloc.

Le contrôle *avant* la transaction reste utile (message d'erreur clair et rapide pour le cas courant, sans effet de bord), mais c'est bien le contrôle conditionnel *dans* la transaction qui empêche réellement une survente en cas de concurrence — les deux se complètent, aucun des deux ne suffit seul.

## N° de commande / N° de marché (décision actée 2026-09-10)

Chaque vente peut porter un `orderNumber` (Bières/Vins/Sucreries — rattachement à `Purchase.orderNumber`) et/ou un `marketNumber` (Poulets/Poissons/Plats africains — rattachement à `Expense.marketNumber`), saisis dans le sous-formulaire Paiement — commun à la Caisse (`pos_page.dart`) et à une addition de Table (`table_order_page.dart`, même `showPaymentDialog`/`fetchLastOrderNumber`/`fetchLastMarketNumber`, aucune différence entre les deux écrans) : un seul champ de chaque, pour **toute la vente**, jamais par ligne — si le panier mélange les deux groupes, les deux champs s'affichent ensemble. Comme `Purchase.orderNumber`/`Expense.marketNumber`, ce sont de simples suggestions éditables (`GET .../sales/last-order-number`/`last-market-number`, jamais imposées ni vérifiées contre une commande/dépense existante) — `CreateSaleDto` les accepte en option et `SalesService.create` les écrit telles quelles sur `Sale.orderNumber`/`Sale.marketNumber` (migration `20260910200000_add_sale_order_market_number.sql`). Objectif : permettre de déterminer a posteriori, hors périmètre de cette phase, le bénéfice réalisé par commande/marché plutôt que seulement de façon agrégée.

Repli intentionnel si la suggestion échoue (hors ligne, permission manquante) : le champ reste vide mais éditable, jamais bloquant — même principe que `PurchasesService.nextOrderNumber`.

**Correctif (2026-09-13)** : `lastOrderNumber`/`lastMarketNumber` triaient par `createdAt` décroissant (la ligne la plus récemment **insérée**) plutôt que par le numéro lui-même — or une commande d'achat ou une dépense « Marché » peut être saisie après coup (date librement modifiable, voir `docs/api/purchasing.md`/`docs/api/expenses.md`), donc l'ordre d'insertion ne reflète pas forcément le numéro le plus élevé réellement en usage. Corrigé pour trier par `orderNumber`/`marketNumber` décroissant, exactement comme `PurchasesService.nextOrderNumber`/`ExpensesService.nextMarketNumber` le font déjà côté suggestion de **nouveau** numéro — les deux mécanismes utilisent maintenant la même convention. `lastMarketNumber` exclut aussi explicitement les dépenses « Marché » sans numéro renseigné (`marketNumber: { not: null }`, un champ non obligatoire même pour cette nature).

## `SalesService.refund`

Une vente n'est **jamais supprimée**, seulement marquée `voidedAt` (colonne ajoutée par la migration `20260905210122_add_sale_voided_at.sql`) — piste d'audit conservée. Le remboursement : restocke chaque article (mouvement `in`, motif `Remboursement vente <id>`), et si la vente comportait un paiement crédit, réduit le solde du client du montant crédité pour cette vente précise (clampé à 0, plutôt que de faire échouer un remboursement pour un désalignement comptable mineur — différent d'`applyRepayment`, qui reste strict pour un remboursement volontaire initié par le client).

**Correctif (2026-09-14)** : `PosRepository.refund` existait côté Flutter depuis l'origine mais n'était relié à aucun bouton — endpoint testé et fonctionnel, mais injoignable depuis l'application. Découvert lors d'une vérification en conditions réelles (vente test créée pour valider une autre fonctionnalité, sans moyen de l'annuler proprement). Un bouton « Rembourser cette vente » (icône retour, avec confirmation — action irréversible) a été ajouté sur chaque carte de `sold_items_page.dart`, à côté du montant total.

## Vente à l'unité en plus du lot (décision actée 2026-09-14)

Demande utilisateur explicite (ex. Heineken 33/Despé 33, normalement vendues par lot de 3 à 2 000 FCFA) : permettre aussi la vente d'une seule bouteille, à un prix différent (700 FCFA) — sans en faire un produit à prix variable (le champ `unit` reste un simple texte libre, ex. "3", purement informatif).

Nouveau champ optionnel `Product.unitSalePrice` (migration `20260914215024_add_product_unit_sale_price.sql`), renseigné dans le formulaire produit (« Prix de vente à l'unité (optionnel) », catégories à prix par casier uniquement) — `null` : comportement inchangé, aucune option de vente à l'unité. Comme pour `salePrice`, **le client ne devient jamais source de vérité sur le prix** : `CreateSaleDto.items[].sellAsUnit`/`AddOrderItemDto.sellAsUnit` sont de simples booléens — le caissier indique laquelle des deux tarifications *déjà connues du serveur* s'applique, jamais un montant. `SalesService.create`/`OrdersService.addItem` résolvent le prix réel eux-mêmes : `unitSalePrice` si `sellAsUnit` est vrai et que le produit en a un, sinon `salePrice` comme d'habitude.

Côté Flutter, `PosPage._addToCart`/`TableOrderPage._addProduct` proposent un choix (« Lot (3) — 2 000 FCFA » / « Unité — 700 FCFA ») dès qu'un produit a un `unitSalePrice` — avant même la logique de panier existante. `CartLine.sellAsUnit` (Caisse) mémorise le choix pour l'envoyer avec la vente ; côté Table, `OrderItem.sellAsUnit` (nouvelle colonne, migration `20260914215616_add_order_item_sell_as_unit.sql`) le mémorise sur la ligne d'addition pour que le checkout applique la même tarification à la vente finale — le prix stocké sur `OrderItem.unitPrice` suffirait presque à le déduire (700 ≠ 2000), mais un booléen explicite reste plus robuste qu'une comparaison de montants.

## Correction d'une vente déjà enregistrée (décision actée 2026-09-14)

Demande utilisateur explicite : pouvoir corriger une erreur de caissier après coup, sans passer par un remboursement complet — deux corrections indépendantes, jamais une réconciliation automatique des montants entre elles :

- **`PATCH .../sales/:saleId/items/:itemId`** (`SalesService.updateItemQuantity`, `pos.correct`) : corrige le nombre de produits vendus d'une ligne. Le stock est ajusté par la **différence**, jamais via un mouvement `adjustment` (qui fixerait le stock à une valeur absolue plutôt que de le corriger relativement, voir `stock-math.ts`) — quantité augmentée : décrémente le stock restant comme une vente normale (`out`, refusé si le stock ne suffit plus, `ConflictException`) ; quantité diminuée : restocke la différence (`in`), même logique que `refund` mais partielle. `subtotal`/`total` sont incrémentés du même montant (préserve la remise déjà appliquée, stockée comme un montant figé). **Ne touche jamais aux paiements** : un écart entre le nouveau total et la somme des paiements reste possible après une correction de quantité, documenté plutôt que corrigé automatiquement.
- **`PATCH .../sales/:saleId/payments/:paymentId`** (`SalesService.updatePaymentMethod`, `pos.correct`) : corrige le mode de paiement (Espèces/Mobile Money uniquement) d'une ligne déjà enregistrée — le montant ne change jamais ici.

Les deux refusent une vente déjà remboursée (`voidedAt` non nul, `ConflictException`) — cohérent avec `refund`, qui reste la seule façon d'annuler une vente entièrement.

**Correctif (2026-09-16)** : les deux routes ci-dessus exigeaient `pos.refund` depuis leur création — même permission que l'annulation complète d'une vente, sur l'hypothèse (2026-09-14) qu'« une correction sur une vente déjà enregistrée est tout aussi sensible ». Sur demande explicite de l'utilisateur (« Donne la permission au rôle Serveur de modifier le mode de paiement... et la quantité vendue... »), cette hypothèse ne tenait plus : accorder `pos.refund` au Serveur lui aurait aussi donné le droit d'annuler entièrement une vente, bien au-delà de ce qui était demandé. Nouvelle permission **`pos.correct`**, désormais seule exigée par ces deux routes — `pos.refund` reste seule à gater `POST .../sales/:saleId/refund`. Accordée à tous les rôles qui portaient déjà `pos.refund` (Super Administrateur, Administrateur, Propriétaire, Gérant, Caissier — pour ne rien leur retirer), **et désormais aussi au Serveur**, qui reste volontairement sans `pos.refund` : il peut corriger une vente mais toujours pas l'annuler. Rejoué en production (additif + une nouvelle permission ne peut être héritée rétroactivement par un rôle à accès complet sans réinsertion explicite, même limitation que pour `losses.manage`/Serveur le 2026-09-15) — vérifié en base : `pos.correct` posé sur les 6 rôles voulus, `pos.refund` inchangée (5 rôles, Serveur toujours absent).

Côté Flutter, `CategorySoldItemsPage` (Caisse et Addition) reçoit désormais `roleName` (propagé depuis `HomeDashboard` via `PosPage`/`FloorPlanPage`/`TableOrderPage`) : le bouton « Rembourser cette vente » est masqué pour tout rôle sans `pos.refund` (`canRefundSale`, fonction pure testée sans réseau) — même exception à la convention par défaut de l'application (jamais de masquage client, un refus serveur suffit) que pour Utilisateurs/Catalogue, pour ne pas laisser un bouton voué à un 403. Les icônes de correction (quantité, mode de paiement) restent toujours affichées : tout rôle atteignant cet écran a `pos.sell`, et tous les porteurs de `pos.sell` ont désormais aussi `pos.correct`.

**Correctif (2026-09-15)** : le bouton unique (icône liste, `lib/pos/sold_items_page.dart`) listait toutes les ventes du jour sans filtre ni total ni choix de date — remplacé, sur demande explicite de l'utilisateur, par deux boutons dédiés en haut à droite de la Caisse et de l'écran Addition : **« Boissons vendues »** (Bières/Vins/Sucreries, `Product.hasCasePricing`) et **« Plats vendus »** (Plats africains/Poissons/Poulets, `Product.hasVariablePricing`) — même découpage par catégorie que les exports Excel de Rapports (voir `docs/api/reports.md`). Chaque bouton ouvre `lib/pos/category_sold_items_page.dart` (les deux partagent ce même fichier, via les fabriques `CategorySoldItemsPage.plats`/`.boissons`) : une date choisie (icône calendrier, `showDatePicker`, jour courant par défaut), le **total en gras** des montants du groupe affiché en tête de liste, puis les ventes de ce jour comportant au moins une ligne du groupe — mêmes actions de correction que l'ancien listing (quantité, mode de paiement, remboursement complet), reprises à l'identique sur demande explicite de l'utilisateur plutôt que perdues dans le remplacement.

Toujours `GET .../sales?day=` (route déjà existante, aucun nouvel endpoint) — le filtrage par catégorie et le calcul du total se font côté client (`matchingSalesWithTotal`, logique pure testée sans réseau) en croisant avec `GET .../products` (déjà nécessaire pour la Caisse). Une vente mêlant les deux groupes (ex. une Heineken 33 et un Poulet braisé) n'affiche, dans chacun des deux listings, que ses lignes du groupe concerné — mais un remboursement y annule toujours la vente **entière**, montant total réel annoncé dans la confirmation.

**Correctif (2026-09-17)** : constaté par l'utilisateur en conditions réelles — pour une vente mixte (ex. Foutou Sauce + Chill + Bock, payée 3 300 FCFA en Mobile Money), le montant affiché en tête de chaque carte (et à côté du mode de paiement) était `sale.total`/`payment.amount`, c'est-à-dire le montant de la vente **entière**, identique dans les DEUX listings (« Plats vendus » ET « Boissons vendues ») — alors que chaque carte n'affiche que les lignes de son propre groupe. Résultat : la carte « Boissons vendues » de cette vente affichait 3 300 FCFA alors que ses lignes (Chill 500 + Bock×3 1 800) ne totalisent que 2 300 FCFA, laissant croire à une erreur de calcul.

Corrigé en distinguant clairement deux montants, sans jamais fabriquer de chiffre ne correspondant à aucune donnée réelle (un paiement mixte ne peut pas être scindé de façon fiable entre catégories — pas d'allocation au prorata façon « Marché », voir `docs/api/charts.md`, contrairement à un coût qui peut légitimement être approximé) :
- Le montant en tête de carte (`lineItemsTotal`, fonction pure) est désormais la somme des seules lignes affichées dans **cette** carte — 2 300 pour Boissons, 1 000 pour Plats dans l'exemple ci-dessus — jamais `sale.total`.
- Détection d'une vente mixte : `items.length != sale.items.length` (le nombre de lignes affichées après filtrage est inférieur au nombre total de lignes de la vente). Le cas échéant, une précision apparaît sous l'en-tête (« Vente mixte, avec d'autres catégories — total réel de la vente : 3 300 FCFA ») et chaque ligne de paiement affiche « (vente entière) » à côté de son montant — le montant du paiement lui-même n'est jamais modifié : c'est une vraie donnée de transaction (utile pour `_editPaymentMethod`/la réconciliation), seul son étiquetage change pour ne plus laisser croire qu'il correspond aux seules lignes affichées.
- `matchingSalesWithTotal` (total agrégé de la page) était déjà correct — c'est uniquement le sous-total **par carte** qui était en cause.

## UI Flutter

[lib/pos/pos_page.dart](../../apps/web/flutter/lib/pos/pos_page.dart) : cartes produits (recherche + filtre catégorie), panier avec quantités, bouton Encaisser. [lib/pos/payment_dialog.dart](../../apps/web/flutter/lib/pos/payment_dialog.dart) : paiement simple ou mixte (plusieurs lignes Espèces/Mobile Money — Carte/Crédit retirés le 2026-09-10, voir `CHANGELOG.md`), champs N° de commande/N° de marché conditionnels (voir ci-dessus), solde restant affiché en direct. [lib/pos/receipt_page.dart](../../apps/web/flutter/lib/pos/receipt_page.dart) : reçu imprimable à l'écran.

**Un seul bouton « Valider le paiement » (décision utilisateur du 2026-09-13)** : le bouton distinct « Ajouter la ligne de paiement » a été retiré — pour un paiement à un seul mode (l'écrasante majorité des cas), le montant est déjà pré-rempli au total, donc un seul clic sur « Valider le paiement » enregistre la ligne et ferme aussitôt le dialogue. Le bouton reste toujours actif (plus besoin d'atteindre un solde nul au préalable). Un paiement fractionné reste possible sans bouton dédié : tant qu'un solde subsiste après avoir enregistré la ligne courante, le dialogue reste ouvert (montant suivant pré-rempli avec ce solde) pour la ligne suivante — le nombre de clics pour un paiement fractionné est inchangé, seul le bouton « Ajouter la ligne » distinct a disparu.

**Le paiement à crédit n'est pas encore exposé dans l'UI** : l'activer correctement nécessite un sélecteur de client, qui est le sujet de la Phase 11 (Clients/Crédits). L'exposer maintenant avec un champ « ID client » en texte libre aurait été une UI trompeuse ; le backend le supporte déjà (`payments: [{ method: 'credit', ... }]`), seule l'interface manque.

**Contour rouge sur une vignette en rupture de stock (décision actée 2026-09-16)** : `PosProductTile` (`lib/pos/product_grid.dart`, partagé par Caisse et l'écran Addition via `ProductGrid`) affiche un contour rouge (`AppColors.alert`, même couleur que l'état « Rupture » du module Stock) dès que `product.stockQuantity <= 0` — simple repère visuel, aucun blocage : le produit reste cliquable et ajoutable au panier comme avant, sur demande explicite de l'utilisateur (« indiquer », pas « empêcher »). S'applique uniformément à toutes les catégories, y compris à prix variable (Plats africains/Poissons/Poulets) — `stockQuantity` est un champ générique du produit, indépendant de la tarification.
